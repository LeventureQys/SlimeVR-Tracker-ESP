### 自决区（不阻塞）

#### Q1. Qt 技术栈与运行平台
- 问题描述：用户要求改写为 Qt 版本，但未指定 Qt 主版本、界面技术与目标桌面系统。
- 自决方案：采用 Qt 6、C++17、Qt Widgets、Qt Bluetooth 和 CMake，优先支持 Windows 桌面运行。
- 自决理由：仓库根项目已使用 Qt6 Widgets；目标功能是设备扫描、连接和数值表格展示，不需要 QML 或图形渲染，Qt Widgets 更符合现有技术栈。Qt Bluetooth 提供跨平台 BLE Central API，可直接替代 Android GATT 调用。
- 风险预警：目标电脑需要 Qt Bluetooth 支持及可用的 BLE 适配器；Windows 蓝牙驱动行为可能影响真实设备连接。
- 备选方案：Qt 5.15 也可实现，但会引入 API 兼容分支，且与仓库当前 Qt6 技术栈不一致。
- 置信度：96%。

#### Q2. “不需要界面渲染”的功能边界
- 问题描述：用户要求实时拿到各种数值并展示在界面上，同时说明不需要界面渲染。
- 自决方案：将“不需要界面渲染”解释为不做三维姿态模型、曲线、动画和定制绘制，只提供标准 Widgets 数值界面；界面包含设备列表、连接状态、实时字段和值/单位。
- 自决理由：实时“展示在界面上”仍要求最小 GUI；标准文本、表格和按钮不属于姿态可视化渲染。
- 风险预警：若用户实际要求完全无 GUI，则应改为控制台程序，但这与“展示在界面上”冲突。
- 备选方案：只输出控制台日志；不推荐，因为不能满足界面实时展示要求。
- 置信度：95%。

#### Q3. Qt 版本的设备功能范围
- 问题描述：Android 示例除读取数据外，还包含恢复出厂、回传速率、带宽、角度归零和磁场校准等写配置操作；用户明确强调只需实时数值展示。
- 自决方案：v0.1.0 仅实现扫描、筛选、连接、订阅、周期读寄存器、断开和实时数值展示，不实现会修改传感器状态的配置命令。
- 自决理由：严格遵循用户提出的只读实时展示范围，避免恢复出厂或校准等误操作；后续可按需增量加入配置功能。
- 风险预警：部分设备若默认未开启姿态自动回传，可能需要额外初始化命令；原 Android 示例未发送开启自动回传命令，故当前按设备默认行为实现。
- 备选方案：完整移植所有配置按钮；会超出当前明确需求并增加硬件误配置风险。
- 置信度：94%。

#### Q4. 实时数据字段与单位
- 问题描述：需要明确“各种实时数值”的具体范围和协议换算规则。
- 自决方案：展示 Android `DeviceModel` 已解析的全部字段：三轴加速度 `AccX/Y/Z`（g）、三轴角速度 `AsX/Y/Z`（°/s）、三轴角度 `AngleX/Y/Z`（°）、三轴磁场 `HX/HY/HZ`（沿用设备协议标定）、电量（%）、温度（℃）、固件版本，以及最近更新时间和帧计数。
- 自决理由：源项目 `README.md` 和 `DeviceModel.java` 对这些字段及公式有明确实现，可直接作为 Qt 版协议依据。
- 风险预警：磁场单位在源项目中未明确；Qt 版不会臆造单位，将显示为“协议值”。电量由电压分段估算，并非设备直接报告百分比。
- 备选方案：仅展示九轴姿态字段；会遗漏源示例明确支持的磁场、电量、温度和版本。
- 置信度：98%。

#### Q5. BLE 协议与数据流
- 问题描述：Qt 版本必须确认真实 BLE 服务、特征及通知帧解析方式。
- 自决方案：使用 Service `0000ffe5-0000-1000-8000-00805f9a34fb`、Notify `0000ffe4-0000-1000-8000-00805f9a34fb`、Write `0000ffe9-0000-1000-8000-00805f9a34fb`；解析 `0x55 0x61` 20 字节姿态帧和 `0x55 0x71` 20 字节寄存器返回帧；连接后周期读取 `0x3A`、`0x64`、`0x40`、`0x2E`。
- 自决理由：以上 UUID、命令和换算公式均来自原项目 `DeviceModel.java`，没有协议猜测。
- 风险预警：原 Android 解析器只解析单次通知内的完整 20 字节帧，无法稳健处理 BLE 分包/粘包；Qt 版应使用跨通知缓存与帧头同步以修复该问题。
- 备选方案：逐通知直接按 20 字节解析；实现与原版一致但鲁棒性较差，不采用。
- 置信度：99%。

#### Q6. 多设备支持
- 问题描述：原 Android 示例支持发现并连接多个 `WT` 前缀设备，用户未限定设备数量。
- 自决方案：保留多设备发现能力，但界面一次选择并连接一个设备；切换设备前先断开当前连接。
- 自决理由：桌面诊断工具的一次单连接模型可避免多个 BLE 设备并发轮询、写队列和 UI 数据归属复杂化，同时不影响发现不同设备。
- 风险预警：不能同时监控多个 IMU；若活动骨架需要多节点同步采集，应在后续版本设计专门的多连接会话和时间同步机制。
- 备选方案：首版直接支持多连接并发；属于明显扩展范围，需要额外定义设备上限、刷新策略和同步要求。
- 置信度：91%。

#### Q7. 测试与真实硬件约束
- 问题描述：开发规范强制新数据流执行单元测试和启动测试，但自动化环境不保证存在兼容 WIT BLE 设备。
- 自决方案：协议解析器采用与 BLE 解耦的纯 C++/Qt 类并编写 QtTest，覆盖正常帧、分包、噪声、边界电量和版本解析；构建后实际执行桌面程序启动测试。真实扫描、连接和实时数据验收若无设备则明确标记“硬件阻塞”，不默认通过。
- 自决理由：该方案满足可自动验证部分，并严格遵守规范对无法执行硬件测试的记录要求。
- 风险预警：没有真实传感器时，无法证明 Windows BLE 驱动、目标设备 UUID 和通知订阅在本机端到端正常。
- 备选方案：加入模拟数据模式完成 UI 链路测试；可作为测试辅助，但不能替代真实硬件验收，设计阶段再确定是否纳入。
- 置信度：97%。
