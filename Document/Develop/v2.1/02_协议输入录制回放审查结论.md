## 2. 模块结论

**结论：条件通过。**

协议解析、CRC、地址映射和同 sequence 分组总体可信，可作为 V2.1 基础保留。主要缺口不在字节解析，而在“接收时间”和“真实采样时间”被混用，以及 raw 回放无法还原真实逐样本时间语义。

该模块不是巨大 twist 和反关节的首要根因，但会影响积分角度比例、异常间隔和离线算法比较的可信度。

## 3. 已确认正确部分

### 3.1 帧格式

实现与协议一致：

```text
AA 55 ADDR SEQ 12
AX AY AZ GX GY GZ MX MY MZ
CRC_L CRC_H
```

其中：

- 固定 25 字节；
- payload length 为 `0x12`；
- 九轴为大端有符号 int16；
- CRC 为前 23 字节 Modbus CRC16；
- CRC 存储为低字节在前。

### 3.2 流式重同步

parser 能处理：

- 任意起始位置；
- 前导噪声；
- 不完整帧；
- 错误长度；
- 错误 CRC；
- 尾部只保留潜在 `0xAA`。

### 3.3 六路地址和分组

`0x50..0x55` 映射明确，同 sequence 六路完整后继续下游，能够阻止不同采样序号被直接拼成一个手部姿态。

### 3.4 raw 优先录制

保存 `raw.bin` 是正确决策：

- 可以在算法变化后重新回放；
- 不依赖旧派生姿态；
- 能复核 CRC、丢帧和分组；
- 适合 V2.1 建立新算法对照。

## 4. 已证实问题

## I01：同一次 `readAll()` 中所有帧共享一个主机到达时间

SerialDataSource 对一批字节只生成一个 monotonic timestamp，FrameStreamParser 将该时间写入该批中解析出的每一帧。

真实串口以约 200 组/s 连续采样，但 Windows/Qt 可能每隔几十或上百毫秒批量交付多个组。因此：

```text
多个连续 sequence
→ 同一个 receivedMonotonicNs
```

FusionBank 随后把零 dt 回退为标称 5 ms。

这在固定采样率、无丢组时可作为近似，但 `receivedMonotonicNs` 已不再是样本采样时刻。

严重度：**High**。

## I02：sample time 与 receive time 没有分开

`RawImuFrame` 只有 `receivedMonotonicNs`，后续 CalibrationPipeline/FusionBank 把它当作积分时间来源。

应区分：

- `sampleTimestampNs`：设备采样时间；
- `receivedMonotonicNs`：主机收到批次的时间；
- `emittedMonotonicNs`：完整组六路被发出的时间。

严重度：**High**。

## I03：固定 5 ms 对真实采样率存在比例误差

实测组率约 198.3 Hz，对应周期约 5.04 ms。固定 5 ms 的误差不足 1%，单独不足以解释 100° 以上的错误姿态，但会造成可量化的积分比例偏差。

若实际硬件采样率或丢组发生变化，误差会增大。

严重度：**Medium/High**。

## I04：raw 回放不包含逐样本真实时间

raw.bin 只保存原始字节，没有设备采样时刻。回放可以重现：

- 字节顺序；
- CRC；
- sequence；
- 六路分组；

但不能严格重现采集时的主机批量到达和真实设备 sample time。

当前回放“确定性”主要来自算法使用固定 nominal dt，而不是录制完整保存了采样时钟。

严重度：**Medium**。

## I05：派生流需要 schema 升级

现有 fused/observation/skeleton JSONL 没有完整记录：

- 坐标契约版本；
- runtime config hash；
- rig hash；
- sample time 与 receive time；
- 算法版本；
- 分解语义版本；
- 是否执行 neutral/mount calibration。

V2.1 若继续读取旧派生数据，容易把旧错误语义与新语义混用。

严重度：**Medium**。

## 5. 条件性风险

### 5.1 sequence 只有 8 位

sequence 回绕本身已有测试，但当存在长时间断流、旧 pending 和重连时，需要确保新旧同值 sequence 不会混组。

### 5.2 完整组策略

只让完整六路组进入相对姿态是安全基线，但会把单路短时缺帧变成整组等待/丢弃。需要明确：

- 何时继续发完整组；
- 何时交给 skeleton Held/Recovered；
- pending 超限如何记录；
- 重连后是否清空所有时序状态。

### 5.3 主机延迟统计

当前 latency 使用的时间字段不一定表示真实 end-to-end latency。V2.1 应以 receive/emitted/render 分开统计。

## 6. 对用户症状的影响

| 症状 | 本模块贡献程度 |
| --- | --- |
| 反关节 | 无直接关系 |
| flex/abd/twist 串轴 | 无直接关系 |
| 角度幅值略有比例误差 | 有贡献，取决于真实采样率 |
| 批量到达时诊断刷屏 | 已有聚合修正 |
| 长时漂移 | 时间步误差可贡献，但不是主要来源 |
| 回放与实时表现不完全一致 | sample/receive time 未记录时存在风险 |

## 7. V2.1 修复要求

1. `RawImuFrame` 增加 `sampleTimestampNs`；
2. 保留 `receivedMonotonicNs` 用于通信延迟诊断；
3. 优先让硬件协议提供设备时间戳或 sample counter；
4. 若协议暂不改，用 sequence 展开值和配置 nominal period 重建 sample time；
5. 丢组时 sample time 按 sequence 差推进，而不是始终 5 ms；
6. 重连时重置 sequence unwrap、pending 和融合时间基线；
7. raw 录制 metadata 保存 nominal period、实测组率和设备时钟来源；
8. 派生 schema 升级并记录 config/rig/algorithm hash；
9. 回放同时支持“严格样本时间”和“原主机到达节奏”两种模式；
10. 所有时间字段命名体现语义。

## 8. 验收门禁

- 随机分包、粘包、噪声、CRC 错误后解析结果不变；
- sequence 回绕、断流、重连不会混组；
- 同一采样序列使用不同串口批量大小，融合结果一致；
- 198/200/202 Hz 合成轨迹的积分角按真实 sample time 变化；
- 丢 1、2、10 组时 dt 与 sequence 差一致；
- raw 回放能复现同一 V2.1 派生姿态；
- metadata 能说明时间来源和配置版本；
- receive latency 不再被误写为 sample period。

## 9. 最终判断

协议和录制框架是当前项目中相对可靠的部分，应保留。V2.1 重点不是重写 parser，而是补齐采样时钟语义，使融合误差可以量化，并让实时与回放真正共享同一物理时间基准。
