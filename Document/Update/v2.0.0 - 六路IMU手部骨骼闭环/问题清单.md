### Q1：V2.0 主实现载体应以 Python/PySide6 还是 C++/Qt 为核心

- 问题描述：需求文档同时引用 C++/Qt 六路 IMU MVP（`Document/Research/手套IMU解算MVP/src/`）和 Python/PySide6 手部显示软件（`Document/Develop/v2.0/手套姿态解算软件/app/`）。需求文档第 80 行允许“改造为统一骨骼帧显示端”或“将六路解算与骨骼层集成到同一应用”，但未冻结主实现语言与进程边界。该选择会影响协议、融合、VQF、模型加载、线程模型、测试框架和最终部署方式。
- 建议方案：采用“C++/Qt 算法核心 + 明确的进程内接口或稳定 IPC + PySide6 显示端”的分层路线；第一阶段先将 C++ 核心输出版本化 `HandSkeletonFrame`，PySide6 仅消费骨骼帧。理由是现有协议和 Madgwick 核心已在 C++，SlimeVR/VQF 抽取也更接近 C/C++ 生态，同时保留现有 PySide6 GLB 渲染资产。
- 备选方案 A：全部迁移到 Python/PySide6，复写或绑定协议、融合与 VQF；开发体验统一，但需要重做大量已有 C++ 核心并重新验证数值一致性。
- 备选方案 B：全部整合到 C++/Qt，迁移现有 PySide6 GLB 渲染和 UI；运行时部署统一，但 UI 与 GLB 渲染迁移工作量最大。
- 风险预警：如果不先冻结主载体，后续数据契约、线程边界、录制格式和测试体系会反复重构；这属于高返工风险的总体技术路线分歧。
- 置信度：85%。
- 分区归属：置顶区。

### Q3：V2.0 核心验收模型应冻结为 GLB、FBX，还是双模型并存

- 问题描述：需求文档第 595–599 行把最终显示模型选择列为阶段 0 必须确认项；第 691–701 行要求阶段 6 选择并整合 GLB 或 FBX 骨架实现。现有 PySide6 软件已有 `app/assets/generic-hand-left.glb`，而 archived 原型包含 FBX/Assimp 资产和蒙皮实现。两者的骨骼命名、绑定矩阵、网格 offset、坐标系与部署依赖不同。
- 建议方案：核心验收冻结为现有 GLB 模型，`HandSkeletonFrame` 与骨骼配置保持模型无关；FBX 原型仅作为算法与矩阵处理参考，FBX 运行时适配列为兼容性子阶段，不阻塞核心闭环。
- 备选方案 A：核心验收冻结为指定 FBX 模型，需要用户明确目标 FBX 文件和目标工具链。
- 备选方案 B：核心验收要求 GLB/FBX 双模型并存，会显著扩大阶段 6、7 和验收矩阵范围。
- 风险预警：不冻结验收资产会导致骨骼语义配置、绑定姿态、蒙皮矩阵测试与 UI 集成标准无法稳定，后续返工规模大。
- 置信度：88%。
- 分区归属：置顶区。

回复：按照现有GLB模型来吧。
