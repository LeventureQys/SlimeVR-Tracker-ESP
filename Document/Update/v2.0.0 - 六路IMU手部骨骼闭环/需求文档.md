# V2.0 六路 IMU 手部骨骼解算与显示需求文档

## 1. 文档目的

本文定义 V2.0 的最终开发目标、系统边界、数据契约、算法要求、实施阶段和验收标准。

本版本的核心目标不是构建完整的 SlimeVR Tracker，也不是接入 SlimeVR Server，而是利用仓库中已有的六路 IMU 解算 MVP、SlimeVR 姿态算法实现和手部骨架显示原型，建立以下完整闭环：

```text
六路手套 IMU 原始数据
    ↓
协议解析、同步与传感器校准
    ↓
六路姿态融合
    ↓
手腕与五指相对姿态
    ↓
手部运动学约束与骨骼解算
    ↓
统一手部骨骼帧 HandSkeletonFrame
    ↓
FBX/GLB 手部骨架与蒙皮界面实时显示
```

SlimeVR 在本版本中作为姿态融合、静止检测、陀螺仪零偏、温漂处理、坐标转换和异常保护的算法参考来源。SlimeVR UDP、Tracker 注册、Server 握手和完整 VR 数据输出不属于主链路，也不作为本版本验收前提。

## 2. 背景与现有基础

### 2.1 六路原始 IMU 解算 MVP

`Document/Research/手套IMU解算MVP/` 已提供以下能力：

- Windows 串口读取；
- `AA 55` 原始帧同步；
- CRC16-Modbus 校验；
- 六颗 IMU 地址识别；
- 同 `sequence` 六路原子分组；
- 加速度计、陀螺仪和磁力计原始值解析；
- 六路 Madgwick 六轴/九轴姿态融合；
- 六路世界四元数和零位相对四元数；
- 数据有效性、统计和自动化测试；
- 已实现但本版本不要求保留为主链路的 SlimeVR UDP 输出。

原始帧当前约定为：

```text
AA 55 | address | sequence(u8) | length=0x12
      | acc xyz(int16 BE)
      | gyro xyz(int16 BE)
      | mag xyz(int16 BE)
      | CRC16-Modbus(u16 LE)
```

单帧长度为 25 字节，地址范围为：

| 地址 | 语义 |
| --- | --- |
| `0x50` | 手腕/手掌 IMU |
| `0x51` | 拇指末端 IMU |
| `0x52` | 食指末端 IMU |
| `0x53` | 中指末端 IMU |
| `0x54` | 无名指末端 IMU |
| `0x55` | 小指末端 IMU |

### 2.2 当前 PySide6 手部显示软件

`Document/Develop/v2.0/手套姿态解算软件/` 已提供：

- PySide6 桌面界面；
- 25 关节 GLB 手部模型；
- 骨架层级、绑定姿态和逆绑定矩阵；
- GPU 蒙皮；
- 手腕姿态显示；
- 五指 `bend/sway` 驱动；
- 骨长保持和关节运动测试；
- 姿态帧和原始字节流录制。

当前软件接收的是主控已处理的 31 字节姿态帧，而不是六路原始 IMU 帧；桌面端当前不执行姿态融合。V2.0 需要将其改造为统一骨骼帧的显示端，或将六路解算与骨骼层集成到同一应用中。

### 2.3 现有 FBX 手部骨骼原型

`Document/Wit 手套资料/archived/` 已提供一个可复用的 FBX 骨骼研究原型，包括：

- 使用 Assimp 导入带骨架和蒙皮权重的 FBX；
- 保留骨骼父子层级、绑定局部矩阵和逆绑定矩阵；
- 每个网格独立的骨骼 offset 和绑定变换；
- 掌指相对四元数计算；
- 传感器安装旋转修正；
- swing/twist 思路下的屈伸和张合分解；
- 关节锁轴、限位和整链耦合；
- 局部骨骼姿态、全局矩阵和蒙皮矩阵计算；
- 骨长不变和矩阵有效性测试。

该原型目前主要用于运行时 FBX 导入和显示，不包含动画 FBX 文件导出能力。

## 3. 最终目标

### 3.1 核心目标

1. 从真实六路手套 IMU 获取原始九轴数据；
2. 稳定解析并同步六颗 IMU 的同一时刻数据；
3. 对六颗 IMU 分别执行校准和姿态融合；
4. 输出手腕和五根手指的稳定世界姿态；
5. 计算五根手指相对手腕/手掌的姿态；
6. 根据每颗 IMU 的真实安装方向修正局部坐标；
7. 从手指相对姿态中提取屈伸、张合及可观测的旋转分量；
8. 使用人体工程学约束将每根手指的单 IMU 观测分配到多个 FBX 骨骼关节；
9. 生成与具体渲染器和文件格式解耦的 `HandSkeletonFrame`；
10. 使用 `HandSkeletonFrame` 实时驱动带骨架和蒙皮的手部模型；
11. 支持录制原始数据、融合姿态和骨骼帧，以便离线回放与复核；
12. 提供自动化测试、真实硬件测试和验收报告。

### 3.2 质量目标

- 数据链路无无界缓存增长；
- 姿态和骨骼矩阵不出现 NaN、Inf 或零范数四元数；
- 静止时骨骼不得持续抖动或发生明显跳变；
- 手掌整体旋转不应被错误解释为手指屈伸；
- 骨骼父子关系正确，骨长保持不变；
- 关节输出符合配置的轴限制和人体工程学角度范围；
- 丢帧、单路失效、串口重连和磁场异常不会导致程序崩溃；
- 同一份录制原始数据应产生确定、可复核的骨骼结果。

### 3.3 可选目标

以下能力应在核心骨骼闭环通过后独立评估：

- 将骨骼帧导出为 JSON、CSV、BVH 或 glTF 动画；
- 通过 Blender、Autodesk FBX SDK 或其他可靠工具生成带动画轨道的 `.fbx` 文件；
- 将骨骼帧实时发送给 Unity、Unreal 或其他应用；
- 并行保留 SlimeVR UDP 输出；
- 将算法核心移植到 ESP 固件；
- 支持左右手和多副手套。

### 3.4 明确不属于核心范围

- 不要求接入 SlimeVR Server；
- 不要求实现 SlimeVR Tracker 发现、握手和心跳；
- 不要求输出完整 VR 人体数据；
- 不要求使用 SlimeVR Server 的人体骨架算法；
- 不宣称单个指尖 IMU 能直接测得 MCP、PIP、DIP 的独立真实角度；
- 不宣称达到医疗级或光学动作捕捉级精度；
- 不在核心实时闭环通过前直接开展完整 ESP 固件移植；
- 不将“运行时驱动 FBX 骨架”与“写出动画 FBX 文件”混为同一功能。

## 4. 术语与能力边界

### 4.1 传感器姿态

传感器姿态是姿态融合算法输出的单位四元数，描述每颗 IMU 相对参考坐标系的方向。

### 4.2 手指相对姿态

手指运动必须以手腕/手掌为参考，基础公式为：

```text
q_relative = inverse(q_palm_world) × q_finger_world
```

该计算用于消除手掌整体旋转。不得直接把手指世界姿态作为手指关节角。

### 4.3 安装方向修正

每颗 IMU 必须具有独立安装修正四元数：

```text
q_corrected = q_mount × q_relative × inverse(q_mount)
```

具体乘法方向必须通过固定动作测试冻结，并由自动化测试保护。不得通过随意交换四元数分量、取反轴或修改显示代码来掩盖安装配置错误。

### 4.4 骨骼估计

当前每根手指只有一个末端 IMU，不能唯一恢复多个手指关节的真实角度。因此，完整手指骨骼数据属于：

> 由单指相对姿态观测和人体工程学约束生成的多关节骨骼估计。

输出必须通过字段标识其属于 `estimated` 或 `coupledApproximation`，不得描述为每个关节均由硬件直接测量。

### 4.5 FBX 骨骼数据

本版本首先要求生成与 FBX 骨架一一映射的运行时骨骼数据，包括：

- 骨骼名称；
- 父骨骼索引；
- 绑定局部变换；
- 当前局部旋转；
- 当前局部矩阵；
- 当前全局矩阵；
- 蒙皮矩阵；
- 有效性和估计状态。

生成动画 `.fbx` 文件是独立导出能力，不是实时骨骼解算成立的前提。

```text
                       ▼
┌──────────────────────────────────────────────────────────┐

└──────────────────────┬───────────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────────┐
│ Protocol Layer                                           │

└──────────────────────┬───────────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────────┐
│ Calibration Layer                                        │
│ 量程换算 / 轴重映射 / 陀螺零偏 / 温漂 / 磁场校准         │
└──────────────────────┬───────────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────────┐
│ Fusion Layer                                             │
```

## 6. 核心数据契约

### 6.1 RawImuFrame

```text
RawImuFrame
- address: u8
- sequence: u8
- received_monotonic_ns: i64
- acceleration_raw: int16[3]
- gyroscope_raw: int16[3]
- magnetometer_raw: int16[3]
- crc_valid: bool
- all_zero: bool
```

### 6.2 SixImuSampleGroup

```text
SixImuSampleGroup
- sequence: u8
- emitted_monotonic_ns: i64
- samples[6]: RawImuFrame
- complete: bool
- present_mask: u8
```

只有完整六路组才能作为默认融合输入。若后续支持部分更新，必须单独定义策略，不能默默把不同时刻数据拼成同一骨骼帧。

### 6.3 FusedImuPose

```text
FusedImuPose
- sensor_id
- timestamp_ns
- world_orientation_wxyz
- valid
- stale
- fusion_mode: 6D | 9D
- rest_detected
- gyro_bias
- magnetic_health
- calibration_state
```

### 6.4 HandObservationFrame

```text
HandObservationFrame
- sequence
- timestamp_ns
- hand_side
- wrist_world_orientation
- fingers[5]
  - finger_world_orientation
  - palm_relative_orientation
  - mount_corrected_orientation
  - flexion_degrees
  - abduction_degrees
  - twist_degrees
  - valid
  - confidence
```

### 6.5 HandSkeletonFrame

```text
HandSkeletonFrame
- sequence
- timestamp_ns
- hand_side
- skeleton_id
- root_transform
- bones[]
  - bone_name
  - parent_index
  - bind_local_matrix
  - local_translation
  - local_rotation_wxyz
  - local_scale
  - local_matrix
  - global_matrix
  - skin_matrix
  - valid
  - confidence
  - source: measured | estimated | held | recovered
- coupled_approximation: bool
- diagnostics
```

界面、录制器和导出器只消费 `HandSkeletonFrame`，不得直接依赖具体融合算法内部状态。

## 7. 算法要求

### 7.1 协议与同步

1. 支持任意分包、粘包和前导噪声；
2. CRC 失败后能够重新寻找同步头；
3. 未知地址不得污染六路组；
4. 同一 `sequence` 的重复节点必须有明确覆盖或丢弃规则；
5. pending 分组数量必须有界；
6. 序号回绕必须正确处理；
7. 记录每路帧率、完整组率、CRC 错误、丢组和缓存水位。

### 7.2 单位和量程

必须确认真实硬件的：

- 加速度计量程；
- 陀螺仪量程；
- 磁力计比例；
- 原始轴方向；
- 采样周期；
- 温度字段是否可获取。

当前 MVP 的默认量程不得未经验证直接作为最终生产参数。

### 7.3 姿态融合

1. 保留现有 Madgwick 作为基线；
2. 接入或抽取 SlimeVR 中的 VQF 作为重点候选；
3. 两种算法必须使用相同录制输入和统一输出接口；
4. 使用真实单调时间差，异常时才回退标称 `0.005 s`；
5. 输出四元数必须有限并安全归一化；
6. 保持四元数符号连续，避免 `q` 与 `-q` 引起导出曲线跳变；
7. 加速度动态异常时不得造成不可控姿态跳变；
8. 磁场异常时退化为六轴，恢复时应平滑；
9. 融合算法失败时保持上一有效姿态并降低置信度，不得输出非法矩阵。

### 7.4 陀螺仪零偏与温漂

1. 每颗 IMU 独立执行静止检测；
2. 启动静止期估计三轴零偏；
3. 静止时允许受限更新零偏；
4. 运动时冻结或严格限制零偏更新；
5. 不得把缓慢真实手指动作误判为静止；
6. 若硬件提供温度，评估并实现每颗 IMU 的温漂补偿；
7. 所有参数独立保存并与设备身份绑定。

### 7.5 磁力计处理

1. 每颗 IMU 独立执行硬铁校准；
2. 每颗 IMU 独立执行软铁和非正交修正；
3. 记录正常磁场模长参考；
4. 检测模长、方向和磁倾角异常；
5. 使用迟滞状态机避免六轴/九轴频繁切换；
6. 磁场恢复时限制航向修正速度；
7. 校准参数非法时不得进入融合。

### 7.6 掌指相对姿态

1. 手腕/手掌姿态为五指的公共参考；
2. 使用四元数直接计算相对姿态，不得通过欧拉角先相减；
3. 每颗手指 IMU 具有独立安装修正；
4. 拇指和四根长指允许使用不同局部轴定义；
5. 相对姿态和安装修正公式必须由单位测试和真实动作表共同冻结。

### 7.7 屈伸、张合与扭转分解

1. 优先使用 swing/twist 或等价的四元数分解方法；
2. 不允许直接以固定世界欧拉角作为手指屈伸；
3. 屈伸和张合分解顺序必须固定并记录；
4. 分解结果必须针对每根手指配置局部轴；
5. 奇异姿态、反向弯曲和超范围输入必须钳制或降级；
6. 拇指必须使用独立参数和运动模型。

### 7.8 骨骼约束与前向运动学

1. 从 FBX/GLB 资产读取真实骨骼层级和绑定姿态；
2. 只在绑定局部变换上追加局部旋转；
3. 不得通过直接修改指尖位置伪造骨骼动作；
4. 保持骨骼绑定平移和缩放；
5. 每帧从绑定姿态重新求解，避免数值累计；
6. 每个关节定义可用旋转轴、最小角和最大角；
7. 张合默认只作用于手指基部关节；
8. MCP、PIP、DIP 屈伸使用可配置耦合关系；
9. 骨骼参数应允许按用户或手型配置；
10. 输出必须标记为耦合估计；
11. 骨长、矩阵有限性和绑定姿态不变性必须有自动测试。

### 7.9 缺帧与恢复策略

单路暂时失效时，首版采用：

1. 保持上一有效骨骼姿态；
2. 将该手指状态标记为 `held`；
3. 持续降低置信度；
4. 超过配置时间后可平滑回归中立位；
5. 数据恢复时进行限速或短时插值，避免瞬间跳变；
6. 一路失效不得阻断其他有效手指的显示；
7. 若手腕失效，五指相对姿态失去公共参考，应冻结整手相对解算并明确报警。

## 8. SlimeVR 算法借鉴范围

### 8.1 应重点评估和复用

- VQF 六轴/九轴融合；
- VQF 内置静止检测和陀螺偏置估计；
- 独立静止检测算法；
- 陀螺仪温度校准思路；
- 四元数、重力和线性加速度工具；
- 传感器安装 offset 思路；
- 有效性、状态机和配置持久化思路。

### 8.2 复用要求

1. 抽取到 Windows 算法核心时移除 Arduino、网络和全局配置依赖；
2. 保留原许可证要求；
3. 使用固定录制数据验证抽取前后的算法一致性；
4. 不因代码来源于 SlimeVR 就默认参数适合手指 IMU；
5. 参数必须通过手套真实数据重新验证。

### 8.3 不需要进入核心链路

- SlimeVR UDP；
- Server Discovery；
- Handshake；
- Heartbeat；
- SensorInfo；
- RotationData；
- Tracker Type；
- Server 重连；
- SlimeVR 人体节点映射。

上述功能以后可作为并行适配器恢复，但不得耦合到骨骼解算核心。

## 9. FBX/GLB 模型要求

### 9.1 运行时模型要求

模型必须包含：

- 唯一可识别的骨骼名称；
- 正确的父子关系；
- 绑定局部变换；
- 逆绑定矩阵或每网格 bone offset；
- 蒙皮权重；
- 可识别的手腕、拇指和四根长指骨链。

### 9.2 坐标和蒙皮要求

1. 区分模型空间、骨骼局部空间、传感器空间和显示空间；
2. 不允许在多个层级重复应用根变换；
3. 对 FBX 多网格模型保留每个网格独立的 bone offset；
4. 若模型包含网格绑定变换，必须按正确乘法顺序进入蒙皮矩阵；
5. 骨架显示和蒙皮模型必须处于同一坐标空间；
6. 绑定姿态下蒙皮结果应还原原始网格。

### 9.3 模型适配

骨骼语义不得硬编码到某一份匿名骨骼名中。应提供模型配置文件，至少定义：

- 根骨骼和手腕骨骼；
- 每根手指骨链；
- 每个关节的局部屈伸轴和张合轴；
- 角度限制；
- 耦合参数；
- 传感器安装修正；
- 左右手信息。

## 10. 录制、回放与导出

### 10.1 必须录制的数据

每次录制至少保存：

1. 原始串口字节流；
2. 解析后的六路原始九轴数据；
3. 六路融合四元数；
4. 手指相对姿态和安装修正姿态；
5. 屈伸、张合和扭转观测；
6. `HandSkeletonFrame`；
7. 校准、融合模式、磁场健康和置信度；
8. 协议及运行统计；
9. 使用的算法和配置版本。

### 10.2 回放要求

- 回放必须走与实时输入相同的解析、融合和骨骼链路；
- 支持原速、暂停和逐帧；
- 相同输入与配置应得到确定结果；
- 支持切换 Madgwick/VQF 和骨骼参数做离线对比。

### 10.3 FBX 动画导出边界

本版本核心验收只要求产生 FBX 骨架对应的逐帧局部旋转和骨骼矩阵。

若实施动画 `.fbx` 文件导出，应作为独立子阶段，并至少满足：

- 以骨骼局部旋转作为动画轨道源；
- 使用单调时间戳重采样到目标帧率；
- 四元数符号连续；
- 明确坐标系、单位和旋转顺序；
- 导入 Blender/Maya/Unity 后骨骼层级和绑定姿态不变；
- 导出后重新导入并与源 `HandSkeletonFrame` 比较角误差；
- 不通过导出文件反向定义实时算法的数据模型。

## 11. 用户校准流程

首版应明确区分以下校准，不得合并为一个含义不清的“重新标定”：

1. **原始传感器校准**：加速度、陀螺仪和磁力计参数；
2. **陀螺仪启动零偏**：开机静止阶段估计；
3. **IMU 安装校准**：每颗 IMU 相对对应骨段的固定旋转；
4. **手部中立姿态校准**：用户张开手并保持标准姿势；
5. **模型适配参数**：手指关节限位、耦合和手型比例；
6. **显示视角重置**：只影响相机，不改变算法状态。

推荐操作顺序：

```text
加载设备校准参数
→ 开机静止完成零偏估计
→ 佩戴手套
→ 执行中立姿态/安装校准
→ 检查六路有效性
→ 开始实时骨骼解算
```

## 13. 验收指标

以下为初始门槛，可根据第一轮真实数据调整，但调整必须记录依据。

### 13.1 数据链路

- 串口默认 `921600/8N1`；
- 目标采样率约 200 组/秒，以真实硬件为准；
- 正常链路下 CRC 错误率接近 0；
- pending 分组和串口缓存保持有界；
- 序号回绕后持续正常；
- 连续运行 30 分钟无崩溃和无界内存增长。

### 13.2 数值稳定性

- 四元数和矩阵均为有限值；
- 四元数范数误差不超过 `1e-4`；
- 相邻帧四元数保持符号连续；
- 绑定姿态蒙皮顶点误差不超过 `1e-4` 模型单位；
- 父子骨长变化不超过 `1e-4` 模型单位；
- 同一输入和配置重复运行结果确定一致。

### 13.3 姿态稳定性

- 分别记录六颗 IMU，不只记录平均值；
- 静置 10 分钟记录总航向漂移和角度抖动；
- 优化方案相对 Madgwick 初始基线的静置漂移目标降低至少 70%；
- 正常磁环境下九轴 10 分钟绝对 Yaw 漂移优先控制在 `3°` 内；
- 若硬件或环境无法达到绝对指标，必须分别报告六轴、九轴、校准前后结果；
- 不允许通过周期性强制归零掩盖漂移。

### 13.4 相对姿态与骨骼

- 手掌整体绕三个轴运动时，静止手指的相对屈伸变化应尽量接近 0；
- 每根手指单独运动时不得显著驱动其他手指；
- 每个关节输出不超过配置限制；
- 完整握拳时指尖到手掌距离单调缩短；
- 张合主要作用于基部关节；
- 缺失单指数据时其他手指继续正常；
- 数据恢复时不得发生不可接受的瞬时骨骼跳变；
- 输出必须标识关节是估计值而非直接测量值。

### 13.5 实时性能

- 原始解析和融合目标约 200 Hz；
- 骨骼求解目标不低于 100 Hz；
- 界面渲染目标稳定在 30–60 FPS；
- 从完整六路组到骨骼帧生成的桌面端处理延迟目标小于 10 ms，不包含串口硬件缓冲；
- UI 刷新不得阻塞串口读取和融合线程。

## 15. 主要风险与应对

### 15.1 单指单 IMU 的不可观测性

风险：无法唯一恢复 MCP、PIP、DIP 独立关节角。

应对：使用可配置人体工程学耦合、输出估计标记、记录能力边界；如果未来需要高精度独立关节角，增加传感器或外部约束。

### 15.2 真实量程和轴方向未知

风险：量程或坐标错误会让所有后续算法产生系统性偏差。

应对：取得硬件寄存器配置，并通过静止重力、已知旋转和逐轴动作交叉验证。

### 15.3 六颗 IMU 安装差异

风险：同型号 PCB 仍可能因物理安装方向不同导致手指反向、串轴或扭转。

应对：每颗 IMU 独立安装四元数，执行逐路三轴验证，不在显示层硬编码补丁。

### 15.4 磁环境复杂

风险：金属、电机、电源线和计算机造成航向偏移或跳变。

应对：每路独立磁校准、磁场健康检测、六轴退化、迟滞恢复和修正限速。

### 15.5 手套佩戴滑动

风险：IMU 相对骨段的安装关系变化，使既有校准失效。

应对：改善固定结构，提供快速中立姿态检查和重新标定，记录校准时间和置信度。

### 15.6 拇指运动模型过度简化

风险：拇指对掌包含多轴耦合，使用长指模型会明显失真。

应对：拇指使用独立骨链、局部轴、限位和耦合；通过对掌、外展和屈伸动作分别验证。

### 15.7 FBX 坐标和蒙皮差异

风险：模型可能包含多网格、不同 bone offset、根节点缩放和匿名骨骼名，导致网格飞出或骨架比例错误。

应对：复用旧 FBX Demo 中已验证的逐网格 offset 和绑定变换处理；模型语义放入配置文件；增加绑定姿态和远节旋转回归测试。

### 15.8 直接复用 SlimeVR 代码的依赖风险

风险：算法代码可能依赖 Arduino、ESP 全局状态和固件配置。

应对：抽取纯算法接口，保留许可证，使用固定数据集验证结果，不把网络和固件生命周期带入桌面核心。

### 15.9 将实时骨骼与 FBX 文件导出混淆

风险：过早围绕某个导出 SDK 设计核心数据，增加复杂性并限制实时链路。

应对：以 `HandSkeletonFrame` 为唯一核心输出；文件导出作为独立适配器和后续阶段。

## 17. 开发原则

- 先建立可录制、可回放、可量化的基线，再优化算法；
- 传感器融合与骨骼求解必须解耦；
- 骨骼核心与 UI、FBX 导出和 SlimeVR 网络必须解耦；
- 使用四元数计算相对姿态，不通过欧拉角直接相减；
- 每颗 IMU 的校准和安装参数相互独立；
- 每帧从绑定姿态求解骨骼，避免累计数值漂移；
- 任何失效都不得输出 NaN、Inf 或未归一化四元数；
- 所有保持、估计和恢复状态必须显式标记；
- 不以主观视觉观感代替定量测试；
- 不把单指单 IMU 的估计结果描述为多关节直接测量；
- 不需要完整 SlimeVR 网络链路才能获得高质量骨骼输出；
- SlimeVR 仅复用与本目标相关的算法思想和纯算法实现；
- 所有精度结论必须保留原始数据、配置和可复核报告。

## 18. 最终确认结论

本版本确认采用以下主路线：

```text
六路手套 IMU 原始九轴数据
→ 校准与姿态融合（借鉴 SlimeVR 的 VQF、静止检测、零偏和温漂算法）
→ 手腕与五指相对姿态
→ 传感器安装修正
→ 手指运动分量提取
→ 人体工程学约束和多关节耦合
→ FBX/GLB 对应的 HandSkeletonFrame
```
