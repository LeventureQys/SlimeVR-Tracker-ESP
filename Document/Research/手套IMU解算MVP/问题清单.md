### Q1. “实时解算”的最终输出层级

- 问题描述：用户要求制作“实时解算的工具”，并指定参考 `Document/Wit 手套资料/parse_six_imu.py:51` 至 `Document/Wit 手套资料/parse_six_imu.py:168` 的六 IMU 协议解析方法。但该 Python 文件只完成帧解析与同 `SEQ` 分组，没有计算姿态四元数、欧拉角或手指关节角；`Document/Wit 手套资料/串口输出解析协议文档.md:81` 至 `Document/Wit 手套资料/串口输出解析协议文档.md:96` 也只定义九轴原始 `int16`，未给出量程、安装方向和融合算法。
- 建议方案：v0.1.0 MVP 先实现“协议级实时解算”，即串口接收、CRC 校验、九轴原始值解析、六地址映射、按 `SEQ` 聚合、完整性诊断和 Qt 实时展示；将姿态融合与手指关节角作为后续版本。
- 备选方案 A：MVP 同时输出每个 IMU 的姿态四元数/欧拉角。该方案需要用户补充或确认加速度、陀螺仪、磁力计量程，六个 IMU 的安装轴向、采样周期、零位标定和融合算法。
- 备选方案 B：MVP 直接输出五指相对手腕的关节角或驱动手模。该方案除方案 A 的输入外，还必须定义传感器到骨骼的映射、关节自由度、静止手型和约束模型，工作量与风险最高。
- 风险预警：若现在把“解算”误判为仅协议解析，而用户实际需要姿态或骨骼角，后续数据模型、UI 和验收标准会大范围返工；反之，在参数缺失时直接加入姿态融合会产生看似可用但物理意义错误的结果。
- 置信度：88%。
- 分区归属：置顶区；该选择决定核心算法、模块边界、测试数据和界面字段，选错会导致大量返工。

### Q4. 六路同步分组与不完整组策略

- 问题描述：协议要求同一 `SEQ` 的六地址属于同一次采样，Python 参考 `Document/Wit 手套资料/parse_six_imu.py:106` 至 `Document/Wit 手套资料/parse_six_imu.py:138` 使用最多 8 个待处理序号并在超限时淘汰旧组。
- 建议方案：沿用有界待分组策略，集齐六地址立即发布完整组；相同地址重复到达时保留最新帧并计数；超出上限的组作为不完整组淘汰并记录缺失地址。默认上限先设 8，阶段二通过常量明确。
- 备选方案：按固定毫秒超时淘汰；需要根据实测链路延迟选择阈值，可作为后续可配置项。
- 风险预警：仅按到达顺序淘汰时，极端乱序可能过早淘汰；但设备正常顺序输出且参考工具已采用该策略，MVP 风险可控。

### Q7. UI 刷新频率与接收吞吐

- 问题描述：协议输出频率约 200 Hz，六个地址合计约 1200 帧/秒；如果每个有效帧都直接刷新全部控件，GUI 事件队列可能积压。
- 建议方案：串口层和解析层持续处理全部字节，数据模型仅保留最新快照；UI 使用约 33 至 50 ms 的定时器，以 20 至 30 Hz 刷新显示，不丢失解析统计。
- 备选方案：每个完整六路组直接刷新 UI；在 200 组/秒下重绘成本过高，不采用。
- 风险预警：UI 显示不会逐组呈现全部 200 Hz 样本，但实时监看不需要每个视觉帧都显示；如需无损保存，应另增录制模块。
- 置信度：98%。

- 风险预警：如果用户标定姿势不稳定，后续相对姿态会带固定偏差；界面必须显示是否已标定及失败原因。

#### Q18. 不完整采样组对融合器的更新

- 问题描述：某个 `SEQ` 可能缺少一到多个地址。姿态融合可按单帧独立更新，也可只在六路完整组上同步更新。

- 备选方案：各路单帧到达即独立更新；时延更低，但六路姿态不再严格对应同一采样时刻。
- 风险预警：严格完整组策略在单路持续丢失时会冻结全部六路姿态；设计阶段可保留“最后有效姿态 + 缺失状态”以保证 UI 可观察性。
