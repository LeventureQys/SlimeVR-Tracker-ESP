### 自决区（不阻塞）

#### Q1. Qt Bluetooth API 的平台差异
- 问题描述：`QLowEnergyController` 与 Windows BLE 后端存在平台行为差异，服务发现、错误文本和断开时序不能按 Android GATT 回调逐行翻译。
- 自决方案：以 Qt 6 的 `QBluetoothDeviceDiscoveryAgent`、`QLowEnergyController`、`QLowEnergyService` 和信号槽状态机重新实现，不复刻 Android 的线程与回调结构。
- 自决理由：Qt Bluetooth 已定义跨平台 Central API；状态机设计能直接表达扫描、连接、服务发现、通知订阅和断开生命周期。
- 风险预警：仅有真实硬件才能验证目标 Windows 蓝牙驱动的端到端行为。
- 备选方案：使用 Windows WinRT 原生 BLE API；会失去 Qt 跨平台能力并引入平台专用实现。
- 置信度：97%。

#### Q2. 是否加入模拟数据模式
- 问题描述：规范要求启动测试覆盖新功能核心路径，但开发环境可能没有兼容的 WIT 设备。
- 自决方案：加入显式的“演示数据”模式。它生成符合字段约束的确定性快照，只用于验证 UI 更新、状态切换和启动路径；界面持续显示“演示模式”，避免与真实数据混淆。
- 自决理由：模拟模式可在无硬件环境完成可重复启动测试，但真实 BLE 验收仍独立标记为硬件阻塞，二者不会互相替代。
- 风险预警：演示模式不能证明 BLE 扫描、GATT 连接或目标传感器兼容性。
- 备选方案：不提供模拟模式，仅启动空窗口；无法覆盖实时展示核心路径。
- 置信度：96%。

#### Q3. 接收帧校验策略
- 问题描述：原协议帧固定 20 字节，但 Android 示例没有校验和验证，且 `0x55 0x61` 姿态帧的第 20 字节同时被当作 `AngleZ` 高字节，不能假设存在额外校验字节。
- 自决方案：只校验帧头、帧类型、固定长度和寄存器类型；使用跨通知缓存完成同步，不增加源码没有依据的校验和规则。
- 自决理由：严格依据 `DeviceModel.java:205` 至 `DeviceModel.java:293`，避免臆造协议。
- 风险预警：长度正确但内容损坏的帧无法被完整识别；可通过数值范围和后续帧同步降低影响，但不擅自丢弃协议允许的极值。
- 备选方案：查询厂商完整协议后加入校验规则；可作为后续增强。
- 置信度：99%。

#### Q4. BLE 写操作串行化
- 问题描述：连接后需要周期发送四条寄存器读取命令；Qt/Windows BLE 通常不适合并发写特征值。
- 自决方案：使用单线程事件循环中的命令队列，每 500 ms 发送一条命令，按磁场、电量、温度、版本循环；仅在服务进入 `RemoteServiceDiscovered` 且写特征有效时启动。
- 自决理由：与 Android 示例的 500 ms 间隔一致，并避免多个写请求重叠。
- 风险预警：设备断开时未发送的命令必须清空，防止重连后发送陈旧命令。
- 备选方案：一次性连续写四条；存在后端拒绝或设备丢包风险。
- 置信度：95%。

#### Q5. UI 刷新节流
- 问题描述：传感器回传率可达到 200 Hz，逐帧更新多个控件会增加主线程负担。
- 自决方案：解析器每帧更新最新快照并发出数据变化信号；主窗口用 100 ms 定时器最多 10 Hz 刷新数值表，同时帧计数保留真实接收数量。
- 自决理由：与 Android 示例 100 ms 界面刷新周期一致，且满足实时观察需求。
- 风险预警：界面不会逐帧显示，但不会丢失最新状态；本版本不用于原始数据记录。
- 备选方案：每帧刷新 UI；高回传率下可能造成卡顿。
- 置信度：98%。

#### Q6. 独立工程边界
- 问题描述：目标目录位于研究适配器区域，需决定是否接入仓库根 `CMakeLists.txt`。
- 自决方案：创建完全独立的 CMake 工程，不修改仓库根构建和主应用。
- 自决理由：用户指定在 `Adapter/IMU_Example_Qt` 下工作；独立工具可单独配置 Qt Bluetooth，避免给主应用增加不相关依赖。
- 风险预警：需要从目标目录单独执行 CMake，主项目构建不会自动生成该工具。
- 备选方案：通过根 CMake 的 `add_subdirectory` 集成；会扩大变更范围并影响主项目配置。
- 置信度：98%。
